# TabICLv2-DML 实验 GitHub 归档设计

日期：2026-08-28  
状态：已批准，待实施

## 1. 目标

将当前 TabICLv2-DML 实验整理成一个可读、可复现、可核查的私有 GitHub 仓库。仓库不仅保存代码和最终数字，还要记录 Stage 1、Stage 2、Stage 3 和 Stage 3B 的研究目的、配置、执行过程、异常、诊断结论和复现方式，使导师或未来的研究者不依赖聊天记录也能理解整个实验。

仓库名称为 `tabiclv2-dml-experiments`，默认分支为 `main`，首个归档版本标签为 `v0.1-stage3b`。

## 2. 归档策略

采用“Git 仓库保存可读内容，GitHub Release 保存完整原始结果”的分层方案。

普通 Git 历史保存：

- Python 源代码、运行脚本、配置文件和自动测试；
- 项目总览、实验方法、完整复现指南和结果解释；
- 各阶段汇总 CSV、最终报告、关键图表和运行环境记录；
- 实验设计、执行计划和原始结果归档清单；
- 原始结果压缩包的文件名、大小、SHA-256 校验值和生成时间。

GitHub Release 保存：

- Stage 1 至 Stage 3B 的完整原始 JSON 结果；
- 必须保留但不适合进入普通 Git 历史的诊断缓存；
- 原始归档内部文件清单和校验文件。

以下内容不上传：

- `.venv`、Python 缓存、pytest 缓存、Matplotlib 缓存和临时目录；
- 运行日志、烟雾测试结果和能够由脚本重新生成的重复缓存；
- TabICLv2 模型权重及第三方软件文件；
- 两篇参考论文 PDF，避免版权和仓库体积问题；
- 密码、访问令牌、账号凭据和含个人隐私的本机配置。

## 3. 目标目录结构

```text
tabiclv2-dml-experiments/
├── README.md
├── REPRODUCIBILITY.md
├── RESULTS.md
├── ARCHIVE_MANIFEST.md
├── pyproject.toml
├── configs/
├── src/
├── scripts/
├── tests/
├── docs/
└── results/
    └── published/
        ├── stage1/
        ├── stage2/
        ├── stage3/
        ├── stage3b/
        ├── figures/
        └── environment/
```

各部分职责如下：

- `README.md`：研究问题、DML 与 nuisance learner 的简要说明、四阶段路线、主要发现和文档导航。
- `REPRODUCIBILITY.md`：环境安装、硬件要求、完整运行命令、断点续跑方式、结果汇总和常见故障处理。
- `RESULTS.md`：每阶段的实验目的、指标、结果、诊断过程、可支持结论和结论边界。
- `ARCHIVE_MANIFEST.md`：Release 原始归档的内容、文件数量、大小、SHA-256 和恢复方法。
- `results/published/`：只存放适合直接阅读、引用或制表的最终产物。

## 4. 实验记录结构

四个实验阶段使用统一模板记录：

1. 研究问题与待检验假设；
2. DGP、真实处理效应、样本量、维度、重复次数和随机种子；
3. 比较模型、超参数、交叉拟合折数以及 CPU/GPU 分工；
4. 运行命令、输入配置、断点续跑规则和输出位置；
5. 偏差、RMSE、覆盖率、标准误、nuisance MSE 和运行时间；
6. 运行中出现的问题、诊断证据和采取的处理；
7. 当前结果支持的结论及不能推出的结论。

阶段之间的逻辑关系必须明确：Stage 1 用于初筛，Stage 2 用于正式重复验证，Stage 3 定位树状 DGP 的欠覆盖来源，Stage 3B 使用 oracle 与不同 learner 组合确认主要误差来自处理 nuisance function `m(X)` 的估计。

## 5. 数据与发布流程

发布流程如下：

1. 清点现有代码、配置、测试、报告、汇总结果和原始结果。
2. 建立 `.gitignore`，先排除所有已知大文件、缓存、日志和本机环境。
3. 将最终结果复制到 `results/published/`，不修改原始输出。
4. 编写 README、复现指南、结果说明和归档清单。
5. 将需要长期保存的原始结果复制到暂存归档目录，生成内部文件清单，再压缩为一个版本化归档。
6. 计算归档文件的 SHA-256，并把校验值写入 `ARCHIVE_MANIFEST.md`。
7. 重新运行测试，扫描敏感信息，并检查 Git 待提交文件和大文件。
8. 创建本地提交，登录 GitHub，创建私有仓库并推送 `main`。
9. 创建 `v0.1-stage3b` 标签和 Release，上传原始结果归档。
10. 从 GitHub 远程页面和 API 核对仓库可见性、README、提交、标签、Release 和归档校验值。

## 6. 异常处理

- 测试失败：停止提交和上传，先定位根因并重新验证。
- 汇总结果缺失或数量不符：对照配置和原始 JSON 重新清点，不用估算值补齐。
- 发现敏感信息：从工作区副本和 Git 暂存区移除；如已进入提交历史，则在推送前重建本地历史。
- 归档校验失败：删除有问题的归档并从只读原始结果重新生成。
- GitHub 登录失败：保留已验证的本地提交，解决登录后再上传。
- 网络上传中断：通过 `gh` 检查远程状态，只补传缺失内容，不重复创建仓库或 Release。
- GitHub 与本地内容不一致：以通过测试和校验的本地版本为依据，修正远程后再次核验。

## 7. 验证标准

本次归档只有在以下条件全部满足后才算完成：

- 全部自动测试通过；已知警告被如实记录；
- Git 暂存区不包含 `.venv`、缓存、日志、模型权重、论文 PDF 或凭据；
- 关键汇总表、Stage 3B 中文报告、图表和环境记录均可打开；
- README 中的主要结果能够追溯到已提交的汇总 CSV；
- 原始归档的文件清单、文件数量、大小和 SHA-256 与实际文件一致；
- GitHub 仓库为 Private，默认分支为 `main`；
- 远程存在首个提交、`v0.1-stage3b` 标签和同名 Release；
- Release 原始归档能够下载，并通过 SHA-256 校验。

## 8. 范围边界

本次工作只整理和发布已经完成的实验，不重新解释未验证结论，不修改 DGP、模型实现或实验数字，也不新增论文写作内容。若整理过程中发现结果不一致，只记录并诊断，不以手工方式修改结果。
